# NVSE co-save save display name mapping

## Goal

Actual `.fos` save filenames still use the vanilla sanitizer and stay ASCII-safe. tNVSE stores the original multibyte manual-save candidate in the matching `.nvse` co-save, then uses that sidecar data only to classify damaged multibyte manual save basenames as manual saves when the load/save list is built.

This avoids changing `SaveGameData::pName`, the actual load path, delete/rename behavior, or the `.fos` filename itself.

## Implemented path

- `save_name.cpp/.h` have been removed. Their remaining useful sanitizer-hook behavior now lives in `save_display_name.cpp`.
- `save_display_name.cpp` owns both the save-name sanitizer hook and the load-menu recognition hook.
- The sanitizer hook replaces the vanilla save-name sanitizer call at `0x8518BB`. It captures the original candidate as the display name, then runs the vanilla-equivalent filename sanitizer:
  - bytes outside `'0'..'z'` become spaces;
  - blocked ASCII characters become spaces;
  - `"` becomes `'`.
- `save_display_name.cpp` stores a pending `{actualKey, displayNameMb}` record keyed by the sanitized save basename.
- `tnvse.cpp` now sets an opcode base for tNVSE serialization and registers:
  - `NVSESerializationInterface::SetSaveCallback`
  - `NVSESerializationInterface::SetLoadCallback`
  - `NVSESerializationInterface::SetPreLoadCallback`
  - NVSE messaging listener for `kMessage_SaveGame`
- NVSE 6.4.8 source confirms `Serialization::HandleSaveGame` dispatches `kMessage_SaveGame` before opening/writing the `.nvse` co-save, so the callback can use the captured `.fos` path.
- Reverse check: `0x7D6970` calls `0x846900` to populate the entry, then returns the list display string at entry offset `0x14`. This is not the stable co-save lookup key. The stable key is the actual save basename stored at entry offset `0x0`.
- Reverse check: `0x8517C0` builds the manual save filename candidate with `%s %i - %s, %s, %s` and then calls the filename sanitizer at `0x8518D0`.
- Reverse check: `0x851980` recognizes standard manual saves by the localized `Save` prefix plus a space; `0x851A20`, `0x851A60`, and `0x851B00` recognize autosave, quicksave, and systemsave.
- Reverse check: `0x846900` normally keeps the save-header display string at entry offset `0x14`; but if the actual basename is not standard manual/autosave/quicksave/systemsave, it overwrites offset `0x14` with the raw actual basename.
- Therefore, a multibyte localized manual save whose actual basename was damaged by the sanitizer, for example `保存 17 - Artaud, 清泉镇, 00.02.23` becoming `     17   Artaud          00 02 23`, is misclassified as a nonstandard save and displays as a filename row.
- tNVSE patches the `0x851AA0 -> 0x851980` call site so manual-save recognition also accepts ASCII `Save ` basenames and SVDN-backed multibyte manual saves. This does not rename the real `.fos` file and does not directly replace the row text. It only prevents `0x846900` from overwriting the parsed save-header summary with the raw actual basename.
- With that recognition hook in place, standard manual save display continues to be generated by the original parsed-header path, producing the same `Location - Size` summary as autosaves and quicksaves.
- Game-provided C strings used by the reader are bounded before constructing `std::string`. In particular, the buffer filled by `0x84FF30` must have a NUL terminator within the expected limit; otherwise tNVSE abandons replacement and returns the vanilla value.
- The load-menu lookup path now uses the game's own full save-path builder at `0x84FF90` instead of manually appending `actualKey + ".fos"` to the save directory. This keeps sidecar lookup aligned with the formal save manager path, including MO2/usvfs path behavior and the exact sanitized basename.
- `0x84FF30` is called as `__stdcall`, matching the reverse result. The earlier cdecl-style call was not safe for this path.

## Co-save record

Record type: `'SVDN'`

Version: `1`

Payload:

```cpp
UInt32 actualKeyLen;
UInt32 displayNameLen;
UInt32 uiEncoding;
UInt32 codePage;
char actualKey[actualKeyLen];
char displayNameMb[displayNameLen];
```

`actualKey` is the sanitized save basename without path or `.fos`. `displayNameMb` is stored in the current UI Windows codepage, not UTF-8.

If `bUTF8=1` and the original input validates as UTF-8, the display name is converted with the existing UTF-8-to-current-codepage path before serialization. Otherwise the original bytes are stored as already-multibyte UI text.

When reading, matching codepages are used directly. If the stored codepage differs from the current UI codepage, the reader attempts `stored codepage -> UTF-16 -> current codepage`; on failure it falls back to the actual save name.

## Reader behavior

The load-menu recognition path does not call NVSE serialization load APIs. It scans the sidecar directly:

1. Builds the `.nvse` path using NVSE's `.fos -> .nvse` behavior, preserving `.bak` suffixes.
2. Validates the NVSE file header.
3. Iterates plugin headers and chunks.
4. Reads only tNVSE's opcode base and `'SVDN'` records; all other data is skipped.

The internal lookup cache key is the actual save basename. Cache invalidation uses `.nvse` size and last-write timestamp when that metadata is available, and `kMessage_SaveGame` erases the updated key.

Under MO2/usvfs, direct `GetFileAttributesExA` can fail for a virtualized sidecar even when `CreateFileA` can still read it from inside the game process. For that reason, a missing file stamp is not allowed to permanently cache a negative lookup. Positive lookups can still be reused, but negative lookups are retried when timestamp metadata is unavailable.

During actual save loading, the registered load/preload callback does not populate the UI cache. It only consumes/skips tNVSE records from NVSE's serialization cursor. This prevents saves that contain `SVDN` data from entering the game load path with plugin data but no handler.

## Overwrite behavior

If an existing save has a display mapping and an overwrite path only provides the sanitized ASCII actual key, tNVSE preserves the old co-save display name instead of replacing it with ASCII. A newly captured non-ASCII or otherwise different display name still replaces the old value.

## Config

Under `[Main]`:

```ini
bSaveDisplayNameMap=1
```

## Verification notes

- Original project build with `PlatformToolset=v145` still requires the v145 toolset to be installed.
- A temporary local build using installed VS 2022 `v143` completed successfully for `Release|Win32`.
- A `std::length_error` on the same path means a game-filled C string was not safely bounded before conversion. The fixed path rejects overlong/non-terminated save paths and actual keys instead of letting the STL scan past the buffer.

- Overwrite an existing mapped save. Confirm the display name is not lost.
- Test missing `.nvse`, missing `'SVDN'`, corrupt record, and mismatched codepage fallback.
