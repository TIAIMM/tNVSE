# Save display name sidecar store

## Goal

Actual `.fos` save filenames still use the vanilla sanitizer and stay ASCII-safe. tNVSE stores the original multibyte manual-save candidate in a private sidecar store, then uses that data only to classify damaged multibyte manual save basenames as manual saves when the load/save list is built.

This avoids changing `SaveGameData::pName`, the actual load path, delete/rename behavior, the `.fos` filename, or the `.nvse` co-save.

## Implemented path

- `save_name.cpp/.h` have been removed. Their remaining useful sanitizer-hook behavior now lives in `save_display_name.cpp`.
- `save_display_name.cpp` owns both the save-name sanitizer hook and the load-menu recognition hook.
- The save-file builder call at `0x850545` is also wrapped. External custom
  save names (including Stewie Tweaks incremental saves) bypass the manual-save
  sanitizer at `0x8518BB`; when such a name contains high bytes, tNVSE applies
  the same vanilla-equivalent sanitizer before `0x850030` constructs the
  physical path. The original name has already been copied into the save header
  at this point, so only the `.fos`/co-save filesystem identity is changed.
- Hook installation and PostLoad reconciliation support Stewie Tweaks 9.95 and
  newer by NVSE plugin
  version plus live module ownership. It deliberately does not match a DLL
  hash, fixed RVA, or compiled byte prefix, so compatible later builds are not
  rejected merely because their compiler output changed.
- ASCII-only custom save names pass through unchanged. The custom-save safety
  hook remains active when `bSaveDisplayNameMap=0`; that setting controls only
  sidecar capture and load-list recognition.
- The sanitizer hook replaces the vanilla save-name sanitizer call at `0x8518BB`. It captures the original candidate as the display name, then runs the vanilla-equivalent filename sanitizer:
  - bytes outside `'0'..'z'` become spaces;
  - blocked ASCII characters become spaces;
  - `"` becomes `'`.
- `save_display_name.cpp` stores a pending `{actualKey, displayNameMb}` record keyed by the sanitized save basename.
- NVSE messaging `kMessage_SaveGame` provides the `.fos` path. tNVSE resolves the normalized full save path and updates the sidecar store immediately.
- Reverse check: `0x7D6970` calls `0x846900` to populate the entry, then returns the list display string at entry offset `0x14`. This is not the stable lookup key. The stable key is the actual save basename stored at entry offset `0x0`, combined with the normalized `.fos` path.
- Reverse check: `0x8517C0` builds the manual save filename candidate with `%s %i - %s, %s, %s` and then calls the filename sanitizer at `0x8518D0`.
- Reverse check: `0x851980` recognizes standard manual saves by the localized `Save` prefix plus a space; `0x851A20`, `0x851A60`, and `0x851B00` recognize autosave, quicksave, and systemsave.
- Reverse check: `0x846900` normally keeps the save-header display string at entry offset `0x14`; but if the actual basename is not standard manual/autosave/quicksave/systemsave, it overwrites offset `0x14` with the raw actual basename.
- Therefore, a multibyte localized manual save whose actual basename was damaged by the sanitizer, for example `保存 17 - Artaud, 清泉镇, 00.02.23` becoming `     17   Artaud          00 02 23`, is misclassified as a nonstandard save and displays as a filename row.
- tNVSE patches the `0x851AA0 -> 0x851980` call site so manual-save recognition also accepts ASCII `Save ` basenames and sidecar-backed multibyte manual saves. This does not rename the real `.fos` file and does not directly replace the row text. It only prevents `0x846900` from overwriting the parsed save-header summary with the raw actual basename.
- With that recognition hook in place, standard manual save display continues to be generated by the original parsed-header path, producing the same `Location - Size` summary as autosaves and quicksaves.
- Game-provided C strings used by the reader are bounded before constructing `std::string`. In particular, the buffer filled by `0x84FF30` must have a NUL terminator within the expected limit; otherwise tNVSE abandons replacement and returns the vanilla value.
- The load-menu lookup path uses the game's own full save-path builder at `0x84FF90`. This keeps sidecar lookup aligned with the formal save manager path, including MO2/usvfs path behavior and the exact sanitized basename.
- `0x84FF30` is called as `__stdcall`, matching the reverse result. The earlier cdecl-style call was not safe for this path.

## Sidecar store

Path:

```text
Data\NVSE\plugins\tnvse\save_display_names.dat
```

The path is relative to the game root and is not inside the active save directory. One file stores all mappings.

The repository tracks an empty template fixture at `docs\fixtures\save_display_names.dat`. That file is not read by the game; it only documents the initial binary layout. Runtime data belongs at the `Data\NVSE\plugins\tnvse` path above and is ignored by Git.

Store header:

```cpp
UInt32 magic;       // 'SVDN'
UInt32 version;     // 1
UInt32 recordCount;
```

Record header:

```cpp
UInt32 actualKeyLen;
UInt32 savePathKeyLen;
UInt32 displayNameLen;
UInt32 uiEncoding;
UInt32 codePage;
char actualKey[actualKeyLen];
char savePathKey[savePathKeyLen];
char displayNameMb[displayNameLen];
```

`actualKey` is the sanitized save basename without path or `.fos`. `savePathKey` is the normalized full `.fos` path and prevents collisions between profiles or save directories that have the same basename. `displayNameMb` is stored in the current UI Windows codepage, not UTF-8.

If `bUTF8=1`, `uiEncoding=1-4`, and the original input validates as UTF-8, the display name is converted with the existing UTF-8-to-current-codepage path before serialization. At `uiEncoding=0`, UTF-8 conversion remains disabled and raw bytes are stored as Windows-1252. Otherwise the original bytes are stored as already-multibyte UI text.

When reading, matching codepages are used directly. Legacy records whose code page is `0` are interpreted as Windows-1252/ASCII records. If the stored codepage differs from the current UI codepage, the reader attempts `stored codepage -> UTF-16 -> current codepage`; on failure it falls back to the actual save name. New English records write code page `1252`, never `0`.

## Writer behavior

The writer does not use NVSE serialization APIs and does not edit `.nvse`:

1. `kMessage_SaveGame` receives the `.fos` path.
2. tNVSE resolves `{actualKey, savePathKey}` and looks for the pending display-name record captured by the sanitizer hook.
3. If the pending display name is just the sanitized actual key, an existing sidecar display name for that save is preserved.
4. Otherwise the matching record is inserted or replaced in `save_display_names.dat`.
5. The whole store is written to a temporary `*.tnvse.tmp` file and atomically replaces the original store only after the full write succeeds.

English standard manual saves are recognized by the original path or the ASCII `Save ` fallback, so tNVSE does not create no-op sidecar entries for them.

## Reader behavior

The load-menu recognition path reads only the private sidecar store:

1. `0x84FF90` builds the current save path from the actual basename.
2. tNVSE normalizes that full `.fos` path into `savePathKey`.
3. tNVSE searches `save_display_names.dat` for matching `{actualKey, savePathKey}`.
4. If a matching display name looks like a manual-save display candidate, tNVSE lets the original parsed-header row survive.

The internal lookup cache is keyed by `{savePathKey, actualKey}` and invalidated by `save_display_names.dat` size and last-write timestamp. Save/delete/rename messages also clear affected cache entries.

## Delete and rename

- `kMessage_DeleteGame` removes the matching record from `save_display_names.dat`.
- `kMessage_RenameGame` stores the old `.fos` path.
- `kMessage_RenameNewGame` moves the old record to the new `{actualKey, savePathKey}`. If a target record exists, it is replaced.

## Config

Under `[Multibyte]`:

```ini
bSaveDisplayNameMap=1
```

## Verification notes

- Original project build with `PlatformToolset=v145` still requires the v145 toolset to be installed.
- A temporary local build using installed VS 2022 `v143` completed successfully for `Release|Win32`.
- A `std::length_error` on the same path means a game-filled C string was not safely bounded before conversion. The fixed path rejects overlong/non-terminated save paths and actual keys instead of letting the STL scan past the buffer.
- New saves must not write `SVDN` into `.nvse`.

## Test plan

- Save with a GBK/CP936 Chinese name. Confirm the `.fos` filename is ASCII-safe and the load menu shows the parsed location/size summary rather than the raw sanitized filename.
- Confirm `Data\NVSE\plugins\tnvse\save_display_names.dat` contains a sidecar record for the new save.
- Save with UTF-8 Chinese input while `bUTF8=1`. Confirm the store uses current-codepage bytes and the menu does not double-convert.
- Overwrite an existing sidecar-mapped save. Confirm the display name is not lost.
- Delete and rename mapped saves. Confirm the sidecar record is removed or moved.
- Test missing store file, corrupt store file, missing record, and mismatched codepage fallback.
- Regression-test English saves, autosave, quicksave, delete, rename, loading, and scrolling the save list.
- Trigger a Stewie Tweaks incremental save with a CP936 player name. Confirm the
  actual `.fos`, `.nvse`, and `SaveGame` event path are ASCII-safe, the log has
  `custom multibyte save name`, and Dialogue History/ShowOff does not throw
  `_Convert_narrow_to_wide` / Win32 error 1113.
